# Lo-Fi Study Space

A cozy pixel-art study room on the web. Create an account, run Pomodoro sessions, keep a Kanban
board and notes, sketch on a whiteboard, mix ambient sounds, add friends, and study together in
live public rooms on Study Street.

DBW project, JIIT Noida, Odd Semester 2026-27: Labhay Jain, Shaurya Srivastava, Divyam Mittal, Krishna Mittal.

## Stack

| Layer | Choice |
|---|---|
| Frontend | React 19 + TypeScript, Tailwind CSS 4, Vite |
| Backend | Node.js + Express 4 (REST API) |
| Database | PostgreSQL (via `pg`, plain parameterised SQL, no ORM) |
| Real-time | Socket.IO (presence, study rooms, invites) |
| Auth | bcrypt password hashes + JWT in an httpOnly cookie |
| Canvas / audio | HTML Canvas (room scene, whiteboard), Web Audio API (generated sounds) |

## Run it on your computer

You need **Node.js 20.19+** and a **PostgreSQL** database. The easiest database is a free
Neon project (see DEPLOY.md step 1), which you can use for local development too.
A local Postgres install also works.

```bash
# 1. install everything
npm run install:all

# 2. configure the server
cp server/.env.example server/.env
#    then edit server/.env: set DATABASE_URL (and DATABASE_SSL=true for Neon)

# 3. start the API (terminal 1)
npm run dev:server        # http://localhost:3001

# 4. start the React app (terminal 2)
npm run dev:client        # open http://localhost:5173
```

The tables are created automatically the first time the server starts.
To test the social features, open a second browser (or an incognito window) and create a second account.

## Database design

```
users ─┬─< tasks
       ├─< notes
       ├─< study_sessions
       ├─< friendships >─┐   (requester_id, addressee_id → users)
       │                 └── users
       ├─< study_rooms (host_id)
       └─< room_members >── study_rooms
```

- **users**: account, profile (display name, avatar, favourite subject), settings as JSONB, saved whiteboard.
  Case-insensitive unique indexes on username and email.
- **tasks / notes / study_sessions**: one row per item, `ON DELETE CASCADE` from users.
  Ids are UUIDs generated by the client, so writes are idempotent upserts (`INSERT … ON CONFLICT DO UPDATE … WHERE user_id matches`), which also stops one user overwriting another's row.
- **friendships**: a request is a row with `status = 'pending'`; accepting flips it to `'accepted'`. Composite primary key, `CHECK (requester_id <> addressee_id)`.
- **study_rooms / room_members**: every room is recorded with open/close times. A unique index on `room_members(user_id)` enforces "one room at a time" in the database itself.
- Analytics (streaks, weekly chart, best day, top subject) are computed from `study_sessions`.

## REST API

All routes except signup/login need the login cookie. Bodies are JSON.

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/auth/signup` | `{username, email, password, displayName?}` → creates account, logs in |
| POST | `/api/auth/login` | `{login, password}` (login = username or email) |
| POST | `/api/auth/logout` | clears the cookie |
| GET | `/api/auth/me` | full app state for the logged-in user |
| PUT | `/api/me/profile` | `{name, avatar, favSubject}` |
| PUT | `/api/me/settings` | `{settings}` |
| PUT | `/api/me/whiteboard` | `{data}` PNG data URL or null |
| DELETE | `/api/me` | `{password}` → deletes the account and all its data |
| PUT / DELETE | `/api/tasks/:id` | create-or-update / delete a task |
| PUT / DELETE | `/api/notes/:id` | same for notes |
| PUT / DELETE | `/api/sessions/:id` | same for completed focus sessions |
| GET | `/api/friends` | friends (with live presence), incoming and outgoing requests |
| POST | `/api/friends/requests` | `{username}` send a request (or accept theirs) |
| POST | `/api/friends/:userId/accept` | accept a request |
| DELETE | `/api/friends/:userId` | decline, cancel, or unfriend |
| GET | `/api/health` | checks the database connection |

## Socket.IO events

| Direction | Event | Payload |
|---|---|---|
| client → server | `room:create` | `{subject}` → ack `{roomId}` |
| client → server | `room:join` / `room:leave` | `{roomId}` / none |
| client → server | `status` | my timer `{mode, running, remaining, total, subject}` |
| client → server | `invite` | `{toUserId}` (must be an accepted friend, and you must be in a room) |
| server → client | `rooms` | every open room with members and their live timers |
| server → client | `presence` | a friend went online/offline or changed room |
| server → client | `invite` | `{from, roomId, subject}` |
| server → client | `friends:changed` | re-fetch the friend list |

## Security notes

- Passwords are hashed with bcrypt (cost 11); login responses don't reveal whether a username exists.
- The session token is an httpOnly, SameSite=Lax cookie (Secure in production), so page scripts can't read it.
- Every query is parameterised, and every row access is scoped by `user_id`.
- Login and signup are rate-limited (30 attempts per 15 minutes per IP).
- Inputs are length- and type-checked on the server; request bodies are size-limited.

## Known limits (good "future scope" material)

- Live room state is held in one server's memory; running several server instances would need the Socket.IO Redis adapter.
- No email verification or password reset yet (needs an email provider).
- No voice/video in rooms (would need WebRTC).
- Ambient sounds are generated in the browser, not recordings.
